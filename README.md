# SEB Navigator

Автономное веб-приложение. Публикуется содержимое папки `dist`; backend не требуется. Пользователь получает локальный доступ после ввода имени, фамилии и проверки XLSX по структуре `Comm.Code`.

## Стабильные данные

Пользовательские данные хранятся в IndexedDB `seb-navigator-local`, object store `settings`. Стабильные ключи:

- `authorized-profile` — локальный профиль допуска;
- `commission-dataset` — последний принятый оригинал XLSX и разобранные ставки;
- `sales-records` — история продаж;
- `data-schema-version` — версия структуры данных.

Service Worker и его кэш не содержат единственную копию пользовательских данных. При обновлении нельзя переименовывать эти ключи или очищать IndexedDB без явной миграции в `ensureDataSchema()`.

## Правила обновления

1. Сохранять относительные URL, чтобы проект можно было разместить как в корне домена, так и в подпапке.
2. При изменении структуры локальных записей увеличить `DATA_SCHEMA_VERSION` в `dist/assets/core.js` и добавить последовательную недеструктивную миграцию.
3. При изменении обязательных файлов увеличить версию `CACHE` в `dist/sw.js` и обновить список `ASSETS`.
4. Не добавлять исходные комиссии в публичную папку `dist/data`. Комиссии предоставляет пользователь.
5. Не менять правило связи товаров: единственный устойчивый ключ — нормализованный `Comm.Code`.
6. Перед выпуском выполнить:

   `node scripts/verify_security.cjs`

   `node scripts/verify_app.cjs "Data/Фокусы Seb Сентябрь 2026 ит-1.xlsx"`

7. Проверить вход с актуальным XLSX, добавление и редактирование продажи, обзор, экспорт отчёта и сохранность истории после обновления.

## Граница защиты

Статический frontend не может сделать загружаемый каталог секретным от владельца устройства. Локальная авторизация, Service Worker и security headers ограничивают обычный доступ и случайные ошибки, но не заменяют серверную авторизацию. Настоящее сокрытие каталога потребует контролируемой серверной выдачи данных (например, Cloudflare Access/Zero Trust перед всем сайтом).

Каталог публикуется как `dist/data/idx-7f2ae1.bin` — не `catalog.json`. Файл собирается через `python scripts/build_app_data.py`, который сериализует JSON, накладывает поверх обратимый XOR (ключ `seb-navigator-2026-catalog-key`) и кодирует в base64; расшифровка — в `dist/assets/core.js` (`fetchCatalog()`), сразу после локальной авторизации. **Это обфускация, а не шифрование**: ключ лежит открыто в публичном JS-бандле, так что защиты от того, кто прочитает исходники фронтенда, это не даёт. Цель — не отдавать читаемый список товаров и цен тому, кто просто откроет ссылку напрямую, посмотрит вкладку Network «как есть» или полезет через «view source» без анализа кода. Если понадобится вернуть человекочитаемый JSON (например, для другого клиента без этой логики) — там же в `build_app_data.py` заменить вызов `obfuscate()` на прямую запись `catalog_json`, и синхронно поправить путь/протекшн в `dist/sw.js` и оба verify-скрипта (`scripts/verify_security.cjs`, `scripts/verify_app.cjs`), которые тоже читают и расшифровывают `idx-7f2ae1.bin`.
